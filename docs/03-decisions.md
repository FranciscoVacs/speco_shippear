# Decisiones de diseño

- **D1 Determinista primero, LLM opcional.** Reglas + léxico dan resultados reproducibles, testeables y gratis en CI; `/speckit.analyze` ya cubre el enfoque "prompt puro". El LLM refina, no es requisito. Costo: menor recall semántico en el baseline.
- **D2 Sin dependencias en core.** Instalación trivial y menos superficie; el adaptador de modelo es la única parte con dependencias, opcional.
- **D3 "Pasos del plan" = tasks + secciones de plan + entidades/contratos.** plan.md no tiene pasos estructurados (ver doc 01); sólo tasks.md es parseable de forma fiable.
- **D4 Tasks de Setup/Foundational/Polish no se reportan como scope colado.** Son infraestructura transversal por diseño de Spec Kit; sí se reportan tasks con `[USn]` o de fase de story sin ningún FR relacionado.
- **D5 Cada vínculo guarda evidencia y score.** El reporte debe explicar *por qué* se considera cubierto un requisito; evita falsos negativos silenciosos.
- **D6 EARS como vara, con "FR-NNN: System MUST …" aceptado como forma Ubicua.** Spec Kit emite ese estilo por defecto; marcarlo todo como mal formado sería ruido. Severidad baja por patrón no-EARS, alta por ambigüedad/intestabilidad real.
- **D7 Severidades:** bloqueante = bloquea implementar con seguridad (req sin plan, contradicción, NEEDS CLARIFICATION abierto); advertencia = probable defecto (ambiguo, sin AC, scope colado); sugerencia = estilo (forma EARS).
- **D8 Idioma de reglas: ES + EN.** Los términos vagos y verbos modales se detectan en ambos idiomas.
- **D9 Evidencia débil absuelve, no cubre.** Un task que no introduce conceptos nuevos respecto de la spec ("vocab") no se marca como scope colado, pero esa misma evidencia débil NUNCA cuenta para dar un requisito por cubierto. Preferimos un falso hueco a esconder uno real.
- **D10 "Scope colado" = concepto nuevo, no baja similitud.** Un task como `POST /invitations endpoint` no comparte vocabulario con ningún FR pero tampoco agrega nada; `Slack` o `CSV bulk import` sí. Se mide con palabras de contenido ausentes en toda la spec (excluyendo vocabulario técnico: endpoint, service, test…).
- **D11 Testeabilidad vs ambigüedad.** QUA002 (no testeable) = atributo de calidad sin umbral numérico ("fast", "scalable") o sin verbo normativo / con verbo no vinculante ("should"). QUA001 (ambiguo) = palabra vaga que delega la decisión ("appropriately", "etc"). Una métrica numérica en el mismo requisito neutraliza QUA002.
- **D12 Criterio de aceptación = story CON escenarios o SC.** Una story sin escenarios no "absuelve" a los FR de su tema (eso lo reporta QUA005). Se compara contra la story completa y contra cada escenario, tomando el mejor.
- **D13 EARS como sugerencia, salvo lenguaje no vinculante.** "System MUST …" cuenta como patrón ubicuo (es lo que emite Spec Kit). Sólo se sugiere reescribir las formas centradas en el actor ("Users MUST be able to") o sin sujeto del sistema.
- **D14 Contradicciones: heurística determinista + LLM opcional.** Determinista: mismo tema (similitud ≥ 0.5) con cantidades distintas en la misma unidad (con conversión de tiempo) o polaridad MUST / MUST NOT → bloqueante (CON001). El LLM sólo agrega candidatos marcados como advertencia "juicio del modelo" (CON002), nunca bloqueantes: no es reproducible.
- **D15 Capa LLM = `Protocol` de una sola función (`complete(system, user) -> str`).** Sin SDK en el core; el adaptador de Anthropic importa el SDK de forma perezosa. Una UI conversacional futura (p. ej. assistant-ui sobre un backend HTTP) consume los hallazgos como JSON y reutiliza el mismo `LLMClient`; no se construye en esta pasada (North Star).
- **D16 Un único `Report`, tres renderizados.** Texto (humano, un hallazgo por línea), JSON (contrato versionado `schema_version`, claves de severidad en inglés estables: blocker/warning/suggestion) y Markdown (tabla pensada para comentario de PR, North Star). El texto en español es presentación; el JSON es el contrato.
- **D17 Orden determinista:** severidad desc → regla → id con orden natural (FR-2 antes que FR-10). Un reporte reproducible permite snapshots y diffs entre corridas.
- **D18 Exit code configurable (`--fail-on`)**: default falla sólo con bloqueantes; `0` ok, `1` hallazgos sobre el umbral, `2` error de uso/entrada. Pensado para CI futuro sin cambiar el core.
- **D19 Bloquear exige evidencia firme.** Un hueco de cobertura inferido sólo por similitud de texto es *advertencia*; es *bloqueante* si hay trazabilidad explícita en el repo (algún `FR-###` citado en plan/tasks) o si el modelo lo confirmó. Motivo: en un repo real implementado, la heurística léxica daba 7 a 12 bloqueantes falsos por feature (docs/04). Un bloqueante falso cuesta más confianza que un hueco perdido.
- **D20 Recall ponderado además de coseno.** Requisitos y tasks reales son largos y con vocabulario distinto; el coseno penaliza el largo. Se enlaza si coseno ≥ 0.35 o si ≥ 50 % de los términos (ponderados por IDF) del requisito están en un único paso/task.
- **D21 El modelo arbitra sólo lo no cubierto.** Con `--llm`, se consulta por cada requisito no cubierto (hasta 8 candidatos) y por cada task/paso sin requisito; los ids que el modelo invente se descartan; presupuesto de llamadas acotado (60). Sin `--llm` no hay ninguna llamada ni red.
- **D22 La UI sólo consume el JSON.** La app web no analiza nada: muestra `report.to_dict` (docs/05). Tres modos de datos: embebido (HTML exportado), API local (`--serve`, 127.0.0.1, features descubiertas + lista blanca de archivos) y muestras.
